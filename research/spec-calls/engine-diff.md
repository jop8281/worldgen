# Spec calls: engine-diff

- `ChangeKind` gains `item_changed`, which is not in `DESTRUCTIVE`. It covers every change to an existing item that has no specific kind: a route's method, path or pageSize, a job's `every`, any `description`, a task's instruction or difficulty, a decoy's `why`, a decoy added or dropped, and any edit to a fixtures table (reported once for the whole table). Why: the header comment requires every changed item to appear in the delta, and the sketch had no kind for these. Old tests and decoys still rerun on iterate, which catches a route move that breaks them. Reversible: yes.
- `path` points at the value in `before` for a removal or change and in `after` for an addition. A removed state is `[..., 'states', i]` with `i` its index in `before` and `before` the state name. Why: each path then resolves in a real world, so it works as an `IssuePath`. Reversible: yes.
- A field whose `type` changes is one `field_changed` at the field path with both whole definitions. Any other attribute change on a same-type field is `field_changed` at `[..., field, attr]`, including enum `values` (order-sensitive, because order drives sorting) and `initial`. Why: attributes of different types are not comparable. Reversible: yes.
- In a state field, each dropped state is `state_removed`, and added or reordered states are one `field_changed` at `[..., 'states']`. Why: there is no `state_added` kind, and state order drives sorting. Reversible: yes.
- Transitions are compared per from-state as sets of targets, so reordering targets is not a change, and a missing from-state equals an empty list. A changed set is `transition_changed`, which stays destructive even when it only adds a target. Why: the engine enforces membership, not order, and acceptance 3 says any change to transitions is `transition_changed`. Reversible: yes.
- Action `input` maps use the same field rules as entity fields, so dropping an action input is `field_removed` and is destructive. Why: an action input is a field definition, and removing one breaks callers that send it. Reversible: yes.
- `meta` is walked down to the deepest differing value (`['meta', 'clock', 'tick']`), and `key` is the top-level meta property (`clock`). Why: `WorldChange.key` needs a value for meta, and the top-level property groups related changes. Reversible: yes.
- Decoys are matched by index, not by content. Why: decoys have no key, and index matching is deterministic. Dropping the first of two decoys shows up as an edit to decoy 0 plus a removal of decoy 1. Reversible: yes.
- Order is meta first, then `SECTIONS` order, then key in code-unit order, then path step by step (numbers before strings, numbers by value, strings by code unit, shorter path first). Why: acceptance 4 asks for section, key and path order, and a locale-free comparison keeps output identical on every machine. Reversible: yes.
- `before` and `after` share structure with the input worlds instead of copying them. Why: worlds are immutable values, and copying would cost time for no gain. Reversible: yes.
- Tests use a small inline world, because `prod/worlds/helpdesk` does not exist yet. Why: AGENTS.md says to copy the helpdesk world, but it has not been built. Reversible: yes. Switch the fixtures once the golden world lands.
