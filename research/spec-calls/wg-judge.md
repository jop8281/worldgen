- Call: an issue's rank is the index of its owning stage in `STAGE_IDS`, resolved from `ISSUES[code].owner` (`path[0]` for `at_path`) through `SECTION_OWNER`. Owners no stage holds (`meta`, `plan`, `format`, `input`) and `fixtures` (written by code) rank 0 and so block every stage. Why: the earliest stage is the safe place to fix them, matching `ownerOf` in policy.ts, which this file may not import. Reversible: yes, one function (`ownerRank`).
- Call: on a failed report (`ok: false`) only error-severity issues of this stage or earlier are returned. Warnings and `STAGES[stage].done` are not consulted. Why: `done` takes an ok report with a world, which a failed check does not have, and the engine already reports errors first. Reversible: yes.
- Call: on an ok report every error is already absent, so the result is plan coverage gaps for plan lists built by this stage or earlier (entities and routes by model, workflows by workflow, tasks by tasks) plus `STAGES[stage].done`, deduplicated by `code@path`. Why: Acceptance 1 asks for coverage gaps and done issues, and `done` already repeats its own stage's gaps. Earlier stages' `done` rules (for example `action.unexercised`) are not rerun at a later stage. Reversible: yes.
- Call: warnings not named by `done` never block, and a `done` warning is returned with its warning severity. Why: Acceptance 2 says blocking, and the caller decides by membership in this list, not by severity. Reversible: yes.
- Call: result order is engine errors in report order, or coverage gaps in plan order then `done` issues. Why: deterministic output for the loop and its issue-set key. Reversible: yes.
