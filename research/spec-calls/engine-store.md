# Spec calls: engine-store

- A non-EnforceError thrown by the transaction function (a runtime error, or a `ctx.fail` signal until api.ts defines its own) returns `{ ok: false }` with EnforceError 422 `tx.aborted`, message copied and the original kept as `error.cause`. Why: the `transact` signature only allows EnforceError, and acceptance 6 requires `{ ok: false }` for any throw; api.ts can unwrap `cause` to map `ctx.fail` statuses. Reversible: yes.
- Each Tx write validates fully before it touches the overlay, and `delete` plans its whole cascade, restrict and nullify set before applying it. Why: a handler that catches an EnforceError and carries on must not commit half of a refused write. Reversible: yes.
- An absent optional field is stored as `null` unless it has a `default` (`datetime` default `now` is engine time) or is a `state` field (which starts at `initial`). Every row therefore has every declared key. Explicit `null` is still refused on a field that is not `nullable`. Why: list filters and graders see a stable shape. Reversible: yes.
- `required` implies non-null: an explicit `null` on a required field is refused even if `nullable` is true. Why: "required" would otherwise be satisfiable by null. Reversible: yes.
- Create in mode `api` must start a `state` field at its `initial` value (code `state.initial`); mode `privileged` may start at any declared state. Why: a plain POST must not skip the workflow (A-10), while seed and actions need explicit states (engine-seed acceptance 6). Reversible: yes.
- Transitions are measured from the pre-transaction value. For a row created inside the same transaction, its current value inside the transaction counts. Writing the unchanged value back is not a move and is allowed. Why: there is no pre-transaction value for a new row; an echoed PATCH should not fail. Reversible: yes.
- Readonly is strict in mode `api`: any presence of the key is refused, even if equal to the stored value. `id` is never writable in either mode. `created_at` and `updated_at` are readonly in `api` and settable (validated as datetime) in `privileged`, so seed can write history. Why: simplest rule that matches acceptance 4. Reversible: yes.
- Unknown field names in create/update data are refused with 422 `field.unknown`. Why: silently dropping a misspelled field hides bugs from the agent under test. Reversible: yes.
- Unknown entity throws 404 `entity.unknown`; a missing row on update or delete throws 404 `row.not_found`; `get` of a missing row returns null. Reversible: yes.
- `onDelete: nullify` on a ref that is not nullable (or is required) refuses the delete with 422 `field.null`. Why: the store never writes a value its own model forbids; check.ts should flag this combination statically (follow-up for the check unit). Reversible: yes.
- Problems found in one write are collected (all 422 field problems together, in data-key then declaration order); the error code is the first problem's code. A state transition violation, a unique clash (409) or a restrict (409) is raised alone. Reversible: yes.
- Ids sort by length, then code units, so `_10000` follows `_9999`. Why: four-digit padding overflows after 9999 rows. Reversible: yes.
- `stateHash` covers tables and counters only, not `now`, and is a pure-JS 128-bit non-cryptographic hash over canonical JSON (sorted entities, rows by id, sorted keys). Why: engine core may not import node:crypto; the hash is for replay equality, not security. Reversible: yes.
- `transact` never moves `now`; advancing the clock per committed call is api.ts's job. Committed rows are frozen. Reversible: yes.
- Unique checks scan the entity's rows on every write (O(n)). Why: worlds are small; an index would be a second copy of the data. Reversible: yes.
