- Call: `record` is called for the attempt just made, before `decide`. So `attempts[step]` counts that attempt, retry needs `attempts < maxAttempts`, and an issue set is "seen twice" when its key appears twice in `seenIssueSets[step]`. Why: the acceptance text does not say which comes first, and this keeps `decide` free of off-by-one adjustments. Reversible: yes, change the two comparisons in `decide`.
- Call: the issue-set "hash" is a canonical string, sorted unique `code@path: found` entries joined by `|` (`issueSetKey`), with each quoted literal in `found` masked as `"*"` (A-124). Why: it is stable under reordering, expected and hint text, and the volatile ids in `found`, while another failing field or row is a different issue, and `StopReason.no_progress.repeatedIssueSet` is a string that stays readable in reports. Reversible: yes, `record` only stores the string it is given.
- Call: `record` has no backtrack flag, so the loop calls a new `recordBacktrack(ledger)` after a `backtrack` decision. Why: `record`'s signature in the type sketch cannot say it was a backtrack, and `decide` reads `ledger.backtracks`. Reversible: yes.
- Call: `backtrack_limit` is returned when `ledger.backtracks >= config.maxBacktracks` and a backtrack is otherwise due. Why: "past config.maxBacktracks" read as maxBacktracks allowed backtracks. Reversible: yes.
- Call: only severity `error` issues block. A rejected outcome with no errors retries. Why: warnings never reject a world, so they cannot decide a backtrack target. Reversible: yes.
- Call: backtrack is checked before no_progress and attempts_exhausted. Why: retrying a step cannot fix issues another step owns, so its attempt budget and seen sets do not apply. A backtrack then clears every step's seen sets, so no_progress counts within one stretch between backtracks (A-124). Reversible: yes.
- Call: owners with no stage map to `plan` (`plan`, `meta`, `format`, `input`), and `fixtures` (written by code) maps to `model`, the first stage that reads it. Why: StepId has no input step, and the earliest step is the safe backtrack target. Reversible: yes, one branch in `ownerOf`.
- Call: `invalid_output` is treated like a rejection that never backtracks, using the outcome's own issues for the set key. Why: those issues describe the proposal's shape, which only a retry of the same step can fix. Reversible: yes.
- Call: `model_error` stops at once with `model_error`. Why: the model client owns transient retries, and policy has no signal to tell a transient error from a fatal one. Reversible: yes.
- Call: the repeated-set stop's `lastIssues` and the exhausted stop's `lastIssues` are the blocking errors of this attempt, or all issues when none block. Why: StopReason needs the issues the user must see. Reversible: yes.
- Follow-up for wg-run-slice: attempts for the backtrack target are not reset by `record`. The loop decides whether a re-run of a step gets a fresh attempt count.
- Call: the loop records `attemptIssueSet(outcome, ownedIssues)` (exported from policy.ts), not `issueSetKey` on raw outcome issues. `decide` uses the same helper internally. Why: `decide` keys only blocking errors, so a caller keying every issue (errors plus warnings) would never match and the run would end as attempts_exhausted instead of no_progress. Reversible: yes, `record` still only stores the string it is given.
