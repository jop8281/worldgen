# Spec calls: engine-openapi

One bullet per call: call, why, reversible. To be folded into research/decisions.md later.

- `openApiOf(world)` lives in engine core (`src/engine/openapi.ts`), is pure, and reads only `meta`, `entities`, `routes` and `actions`. Tasks, graders, solutions, decoys, tests, seed, fixtures and jobs never reach it, and neither do the admin `/_world` routes. Why: the document goes to the agent under test, and graders and solutions must stay hidden from it. Reversible: yes.
- Field JSON Schemas come from `FIELD_JSON`, a table typed `{ [K in FieldType]: (def) => JsonSchema }` in openapi.ts. fields.ts is not touched. A new field type fails to compile until it has an entry here, and `test/openapi.test.ts` pins every type's example definition to a literal schema. Why: the unit may not edit fields.ts, and the table makes a missing type a compile error with no `switch (def.type)`. Reversible: yes (the table can move into `FIELD_TYPES` as a `jsonSchema` member).
- Every entity gets three schemas. `<entity>` is the stored row. It has `id` (pattern `^<idPrefix>_[0-9]+$`), the fields, then `created_at` and `updated_at`, with `readOnly` on engine and readonly fields and `additionalProperties: false`. `<entity>.create` and `<entity>.update` (only when such a route exists) hold just the writable fields. `<entity>.list` is the meta.api list envelope. Action bodies are `<action>.input`. Why: a dot cannot appear in a snake_case Name, so derived names never collide with an entity, and separate create and update schemas say exactly what the store accepts instead of leaning on readOnly semantics that tools read differently. Reversible: yes.
- In a row schema, `required` lists `id`, the timestamps, and every field the store always writes: required, nullable (stored as null when absent) or defaulted (state fields default to `initial`). A value is nullable only when the field is `nullable` and not `required`, which matches the store refusing null on a required field. Reversible: yes.
- `.create` requires a field only when it is `required` and has no default. A state field in `.create` has `enum: [initial]`, because an API create refuses any other start (422 `state.initial`). `default: now` on a datetime is described, not emitted as `default`, since `now` is not a date-time. Query params and path filters carry no null, default or readOnly. Reversible: yes.
- State fields carry `x-transitions` (the declared map) and a description of the allowed moves. Money carries `x-currency` and is an integer in minor units. Phone strings get a description because JSON Schema has no phone format. Email maps to `format: email` and url to `format: uri`. Reversible: yes.
- List params come in this order, matching api.ts: path params, then the declared filters that name a column (a field, `id`, `created_at` or `updated_at`), then `q` (only with `search`), then `sort` (only with sortable fields, enum `f` then `-f`), then the limit param (minimum 1, default pageSize, no maximum because the engine caps larger values silently), then the cursor param. A path param that names a column is a required equality filter. Any other path param is described as unused. Reversible: yes.
- get, update and delete describe `{id}`, or the last param when there is no `{id}`, as the row id, and every other path param as not used to select the row. This is what `rowIdOf` in api.ts does. Reversible: yes.
- Error responses are grouped by status. Each one's schema is the `meta.api.error` template, where an exact `$status` becomes `{ type: integer, const: <status> }`, an exact `$code` becomes the code slot, any other string holding `$status`, `$code` or `$message` becomes a string, and every other value becomes a `const`. Why: the envelope comes from meta.api, and a client sees per status which codes are possible. Reversible: yes.
- Standard operations list a closed set of codes per status (`enum`), pruned by the entity. `field.unique` appears only when the entity has a unique field, `ref.unresolved` only with a writable ref, `state.initial` or `state.transition` only with a writable state field, and `field.required` only when create has a field that must be sent. A delete lists `delete.restricted` only when some restrict ref points into the cascade closure of the entity, and `field.null` only when a nullify ref there is not nullable. `route.not_found`, `method.not_allowed` and `path.invalid` are not per operation. They sit in the top-level `x-error-codes` catalog. Reversible: yes.
- `ENGINE_ERROR_CODES` in openapi.ts catalogs the 21 codes api.ts and store.ts mint today, each with its status. `tx.aborted` is left out because an action turns it into `action.failed` and a standard operation never raises it. Why: the codes are string literals in api.ts and store.ts, and this unit may not edit those files. Follow-up: type `ApiError` and `EnforceError` codes as `EngineErrorCode` so a new code is a compile error. Reversible: yes.
- Actions are tagged `Actions` and answer `2XX` (the handler sets status and body), with an open code list per status. The list is the literal codes the handler passes to `fail(<status>, '<code>'` (found by a static scan and limited to 400, 404, 409 and 422), followed by the engine and store codes a handler's writes can raise. The handler source itself is never emitted. 500 `action.failed` is closed. The description notes that a handler returning its own status of 400 or more sends its own body, not the envelope. Why: the domain codes, such as `ticket.not_pending`, are what the agent under test needs to know, and codes built at run time cannot be listed. Reversible: yes.
- An action with an empty `input` has no request body. Otherwise the body is required when some input must be sent. The body is JSON even on GET, because the engine reads action input from the body only. Path params are documented as `params.<name>`. The query is passed through unvalidated, so it is not documented. Reversible: yes.
- Paths are keyed as the router reads them, with empty segments dropped, so `/tickets/` is `/tickets`. When two endpoints share a method and normalized path, the first in declaration order wins (routes before actions), as in the router. A checked world has no such pair (`route.duplicate_path`). Routes whose entity does not exist are skipped, which only happens in unchecked worlds. Reversible: yes.
- `info.title` is `meta.name`, `info.description` is `meta.description` plus "Resembles <meta.resembles>.", and `info.version` is the constant `"1"`, because a world has no API version. There is no `servers` entry, since the host and port are known only to the serving shell (http.ts). Tags are one per entity, with its description, plus `Actions`. Every entity schema is emitted even when no route exposes it, because action responses may carry any entity. Reversible: yes.
- The response map is a plain object, so integer-like status keys enumerate before `2XX`. JSON key order has no meaning in OpenAPI. Reversible: n/a.
