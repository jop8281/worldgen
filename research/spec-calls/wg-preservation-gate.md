# Spec calls: wg-preservation-gate

- The gate is `preservationIssues(before: CheckedWorld, after: CheckedWorld, edits: readonly WorldEdit[], plan)`. The sketch took `(before, delta, edits, plan)` and the backlog took `(oldWorld, newReport, edit, plan)`. The gate computes the delta itself with `diffWorlds`. `unplannedChanges(delta, edits, plan)` is also exported for callers that only hold a delta. Why: rerunning old tests and decoys needs the new world, and only an accepted world can run them. A failed report has no world, and `blockingIssues` already blocks it. `edits` is a list because an iterate run applies one edit per stage. Reversible: yes.
- A `plan.changes` entry is a dotted path. It is rooted either at the section (`entities.ticket.fields.status`) or at the item key (`ticket.fields.status`), and it covers everything below it. A removed state or enum value is named by its value, not its index (`...status.states.closed`). Entries are trimmed. A bare section name (`entities`) covers nothing. The `iterate.unplanned_change` hint gives the exact dotted name to add. Why: the plan schema says only "every existing item this request changes or removes", and a model needs a format it can copy from the issue. A bare section would allow every removal in that section. Reversible: yes.
- Naming a removed state also covers the edges it takes with it. A `transition_changed` counts as planned when `plan.changes` names its from-state, or names the state of every target it lost. Why: removing a state always removes the transitions into it, so requiring both entries adds noise without adding safety. Naming only the edge still leaves the state removal blocked. Reversible: yes.
- An item named in any edit's `remove` covers every destructive change under it, including a `remove` followed by an `upsert` that replaces the item. Why: decision A-32 says "named in edit.remove", and `remove` names whole items. Reversible: yes.
- An old test is rerun only when the new world dropped it or changed its script. Tests named in `edit.remove` or `plan.changes` are skipped. Why: an unchanged test already passed the new world's own check, so the usual "add refunds" iterate reruns nothing. Reversible: yes.
- Every old decoy of a task the new world kept is rerun and scored by the new world's grader, even when the decoy is unchanged. A task named in `edit.remove` or `plan.changes` is skipped. A decoy is a regression only when it scores exactly 1, which is acceptance 2. Scoring higher than before but below 1 is not a regression. Why: `verifyTask` does not score decoys until engine-verify-full lands, so an unchanged decoy is not yet proven below 1. When it does land, decoys the new world kept unchanged can be skipped. Reversible: yes.
- The reruns go through `checkWorld` on derived worlds, because `#engine` has no export that runs one client script or scores one decoy. Old tests run in a copy of the new world with only those tests and no tasks. Old decoys run as the solutions of copies of their tasks, set to `easy` with no decoys, all in one check. A copy counts as scoring 1 when its task has no `task.solution_not_full_marks` and no issue at its solution or grader. If a derived world stops before the layer that would run the scripts, the gate returns one blocking `iterate.regression` saying the rerun was inconclusive. It never passes silently. Why: this uses only public engine functions. `easy` with no decoys means rules on decoy count cannot block the rerun. Reversible: yes. Replace it with a dedicated engine export (see needs_outside).
- "Rows named by literal ids must survive" (judge.ts header) is implemented as follows. A row id that the old world seeds and the new world does not, and that an old kept test script or task instruction, grader, solution or decoy names as a whole word, is an `iterate.regression` at `['seed', entity]`. Survival is checked by id only, not by row content. Why: a seed rewrite is `snippet_changed`, which is not destructive, so nothing else catches a lost row that an instruction names. The fix belongs to the seed stage. Reversible: yes.
- Issue paths: `iterate.unplanned_change` sits at the change's path in the old world. A test regression sits at `['tests', name]` and a decoy regression at `['tasks', task, 'decoys', i]`. Why: ownership follows the first path step (`ownerRank`), so each issue goes to the stage that can fix it. Reversible: yes.
