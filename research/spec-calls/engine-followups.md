# Spec calls: engine-followups

Review follow-ups from PR #25 (engine-http-cli) and PR #26 (engine-verify-full).

- `errorBody` is exported from api.ts, and http.ts builds its world-envelope replies from it. http.ts keeps a one-line `worldError` that wraps the body in a `Reply`, and no longer has its own copy of the `$status`, `$code` and `$message` substitution. Why: one envelope implementation, as the engine-http-cli follow-up asked. Reversible: yes.
- `ADMIN_PREFIX` (`_world`) and `OPENAPI_PATH` (`openapi.json`) moved from http.ts to api.ts, and check.ts and http.ts both import them. Why: check.ts is engine core and cannot import the shell file http.ts, and the reserved paths must have one source. Reversible: yes.
- `route.reserved_path` is a references-layer error for a route or action whose first path segment is exactly `_world`, or whose segments are exactly `openapi.json` (so `/openapi.json/` counts, as the router and serve both drop empty segments). Why: serve answers those paths on the world port before routing, so in-process tests and verify would pass on a route that HTTP never reaches. Reversible: yes.
- `/openapi.json` is reserved for every method, though serve shadows only GET there. Why: the request said "whose path is /openapi.json", and a POST at the API's discovery path would confuse an agent reading the document. Reversible: yes; narrow it to GET in `reservedBy` in check.ts.
- The `_world` check compares the template's raw first segment. `/_worlds`, `/tickets/{id}/_world` and `/docs/openapi.json` are allowed. A template that spells `_world` with percent-encoding is not caught. Why: the router decodes request segments but compares them to the raw template, so such a route is unreachable anyway. Reversible: yes.
- A path with a `route.bad_path` issue skips the reserved check, and a reserved path skips the id-param and duplicate checks. Why: one fixable issue per cause, as in fix-engine-check. Reversible: yes.
- `task.reference_server_error` replaces `snippet.runtime_error` for a 5xx in the reference solution run. It keeps the same path rule (an action's 5xx points at its handler, any other at the solution), the same `found` (`<METHOD> <path> answered <status>`), and the same hint text, now built from `{ task, call, body }` by the catalog. Owner `at_path`. Why: a distinct code lets WorldGen and reports tell a server failure from a script that threw. Reversible: yes.
- `task.decoy_server_error` is an error for any 5xx in a decoy run, not only when the decoy scores below 1. Path and `found` follow the reference rule: the action's handler when an action answered 5xx, otherwise the decoy's script. One issue per endpoint per decoy run, at its first 5xx. Owner `at_path`. Why: a 5xx means a plausible agent call can crash the world, and a decoy's score is no evidence about the grader once the server failed. Pointing at the handler sends the fix to the code that crashed, as for the reference run. Reversible: yes.
- A decoy with a 5xx is not graded and is not checked for triviality or full marks. If its script also failed (such as an assert on the crashed call), both issues are reported, the 5xx first, as for the reference run. Why: one cause, reported once, with its consequence after it. Reversible: yes.
- A decoy whose call the handler refuses with a 4xx (`ctx.fail`) is still a valid near-miss. Why: refusing bad input is correct world behavior. Reversible: yes.
- AGENTS.md now names `test/docs.test.ts`, not `test/worlds.test.ts`, as the test that fails when `prod/world-format.md` is stale. Why: docs-world-format put the check there and logged this follow-up. Reversible: yes.
