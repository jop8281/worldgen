# Spec calls: engine-sandbox

One bullet per call: call, why, reversible. To be folded into research/decisions.md by engine-freeze, eval-stress-run-2 or docs-design.

- `globalThis` joins SANDBOX_GLOBALS, and the snapshot subtracts `ENGINE_INTERNAL_GLOBALS = ['__worldgenCall']`. Why: the acceptance reads `Object.getOwnPropertyNames(globalThis)` inside the context, and the guarded call needs one fixed global to enter the context with a vm timeout. Reversible: yes.
- A snippet must be exactly one non-class function expression: the source is evaluated as `(source)` and accepted only when the function's own source text equals the trimmed snippet. Leading or trailing comments and wrapping parentheses are rejected. Why: it rejects IIFEs and comma tricks that run code or keep state at compile time, without adding a parser dependency. Reversible: yes.
- Snippets run in strict mode. Why: an implicit global becomes a ReferenceError instead of hidden shared state. Reversible: yes.
- A source that runs past guardMs while being compiled reports `snippet.timeout_guard` from compile, not `snippet.compile_error`. Why: the cause is runaway code, and the catalog hint for that code points at the right fix. Reversible: yes.
- Every function member of ctx counts toward the quota, at any depth (`ctx.now`, `ctx.db.get`, `ctx.time.plus`), including functions inside values a ctx member returns. Data members (`params`, `body`, `fixtures`) are copied, not counted. A snippet that catches the quota fault still ends in it. Why: A-20 makes the quota the verdict budget, so swallowing it must not change the verdict. Reversible: yes.
- Any error object thrown by a ctx member leaves run as the original host error, not only `ctx.fail`. Why: the sandbox cannot tell `ctx.fail` from store enforcement errors or a nested SnippetFault, and store.ts rolls back on any of them. Reversible: yes.
- Snippets are synchronous: creating any Promise during compile or run (calling or returning an async function) faults with `snippet.promise_returned`, even when the Promise is not returned. The host sees each one through a `node:v8` `promiseHooks.onInit` hook that is on only during the guarded call (paused while host ctx members run, so a nested snippet run owns its own Promises). It then marks each one handled in a second guarded call, using the realm's original `then` only when descriptors show the call cannot reach snippet code (unchanged prototype, constructor and species); `util.types.isPromise` stays the check for a returned value. Run uses `microtaskMode: 'afterEvaluate'`. Why: an async rejection the snippet never returned crashed the host process (default `--unhandled-rejections=throw`), and there is no way to know whether a snippet handled its own rejection, while no snippet needs async because every ctx call is synchronous. Changes one earlier test: a snippet that only creates a Promise (to set `Symbol.hasInstance`) now faults instead of returning 1. Reversible: yes.
- When a snippet Promise cannot be marked handled without running snippet code (its prototype, constructor or species was changed), sandbox.ts installs, once per process, an `unhandledRejection` listener that drops rejections of Promises whose prototype chain never reaches the host `Object.prototype`. For a host Promise it keeps Node's default: when it is the only listener and the mode is the default `throw` (read from `execArgv` and `NODE_OPTIONS`), it rethrows the reason as an uncaught exception. Why: the run has already faulted, so the rejection carries no new information, and it must not kill the engine. Limits: other `unhandledRejection` listeners in the process still see the snippet rejection, and `--unhandled-rejections=strict` raises before listeners run. Reversible: yes.
- Every run gets a fresh context, and compile evaluates the source in a throwaway context before accepting it. Why: a source can close the wrapping parenthesis and add top-level `var`, `function`, `let`, `const` or `class` declarations, which a shared context keeps for its whole life (non-configurable globals or the global lexical scope). Snippets can also change intrinsic prototypes (`Array.prototype.x`, `JSON.parse`). A fresh context per run (about 0.2 ms) removes all of these instead of sweeping or freezing, and avoids the override mistake that freezing intrinsics causes. Reversible: yes.
- Values cross the realm boundary as copies. ctx data, values returned by ctx members, and errors thrown by them are copied into the context (errors keep message, name and own primitive fields such as `status`). Arguments to ctx members are copied out as plain host data, and a function or getter in an argument is a `snippet.runtime_error`. A copied error the snippet lets escape, rethrown or not, is mapped back to the original host error. Why: a host-realm object's `constructor.constructor` is the host `Function`, which reaches `process` and `Date`. Stored values are scalars (`Value`), so plain-data copies lose nothing. Reversible: yes.
- Not covered (follow-up): `localeCompare` and `toLocaleString` depend on the host ICU data and default locale. Why left: pinning them changes behavior snippets may rely on. It needs its own decision. Reversible: yes.
- A snippet's result leaves the run as a plain host-data copy made from property descriptors (no getter, `toJSON` or `Symbol.hasInstance` runs on the host). A result containing a function, an accessor, a proxy, an object that is not a plain object or array (a Map, a class instance), or nesting past `MAX_ARG_DEPTH` faults with `snippet.runtime_error` (`a snippet must return plain data: ...` / `a snippet result must be nested at most 64 levels deep`). Arguments to ctx members follow the same plain-shape rule. Why: a getter on a live context-realm result ran with no guard (a `while (true)` there hung the host), and results from fresh realms had different prototypes, so identical runs were not `deepStrictEqual` (a replay check would see false differences). Every `SnippetKinds` result is plain data. Reversible: yes.
- Copying a host value into the context walks its prototype chain for members but stops at any prototype whose own prototype is null (any realm's `Object.prototype`), not only the host one. Why: an object from another realm otherwise brought `hasOwnProperty`, `__proto__`, `toString` and the rest in as own enumerable keys and counted functions. Reversible: yes.
- The vm is not a reviewed security boundary. The copies above close the known host-realm paths. Follow-up: a security review before snippets from untrusted authors run outside eval. Reversible: yes.
- Not covered, BLOCKING for untrusted authors: memory. `node:vm` has no heap limit, and guardMs only bounds time, so `(ctx) => { const a = []; while (true) a.push(new Array(1e6).fill(1)); }` kills the host with a V8 fatal out-of-memory error (about 1 s at the default heap) and no SnippetFault. Why left: bounding it needs snippets to run in a worker or child process with `resourceLimits` and a synchronous bridge for ctx calls, which changes the SnippetHost runtime model and is larger than this item. Until then, the engine runner and eval must not run snippets from untrusted or model authors outside a disposable process (or must run with a small `--max-old-space-size` and treat a crash as a failed run). Reversible: yes.
- ctx arguments may be nested at most `MAX_ARG_DEPTH = 64` levels; deeper is a context-realm error `ctx arguments must be nested at most 64 levels deep` (a `snippet.runtime_error` if uncaught). Any other host error raised while handling a ctx call (such as a host stack overflow when the snippet calls in with almost no stack left) reaches the snippet as a context-realm `Error` with message `a ctx call failed: <host message>`. The host side converts what it can, and the context-side wrapper replaces any host-realm object that still escapes. Why: an unbounded copy overflowed the host stack, and the resulting host `RangeError` exposed the host `Function` and `process`. Stored values are scalars, so 64 levels is far above real use. Reversible: yes.
