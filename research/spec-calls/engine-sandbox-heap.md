# Spec calls: engine-sandbox-heap

One bullet per call: call, why, reversible. To be folded into research/decisions.md by engine-freeze, eval-stress-run-2 or docs-design.

- Snippets compile and run in a `node:worker_threads` Worker created with `resourceLimits` (`maxOldGenerationSizeMb`, `maxYoungGenerationSizeMb`). Defaults live in `SNIPPET_LIMITS` (ctx.ts: 128 and 16 MB), mirrored as `SANDBOX_HEAP_LIMITS` in sandbox.ts; `createVmHost(limits)` takes both as optional overrides. Why: `node:vm` cannot bound heap in-process (engine-sandbox follow-up), and U-5 lets models write snippets. Reversible: yes.
- Heap exhaustion is the issue `snippet.memory` (new in ISSUES, params `{ mb }`, hint `the snippet ran out of memory: its heap is limited to <N> MB`), raised as a SnippetFault at run time and as a failed compile at compile time. Why: Acceptance 1 and 5 (scope widened by the coordinator to issues.ts and ctx.ts). Reversible: yes.
- `npm run docs` (Acceptance 5) works on origin/main (docs-world-format landed). The reference prints every issue code from `ISSUE_EXAMPLES` in code/src/engine/format.ts, whose type requires an entry per catalog code, so the merge adds a `snippet.memory` example (`{ mb: SNIPPET_LIMITS.maxOldGenerationSizeMb }`) there, outside this unit's file list, because the build does not compile without it. `prod/world-format.md` is regenerated and now lists `snippet.memory`. Reversible: yes.
- The snippet worker lives in its own snippet process (`node -e`, spawned with an empty env, unref'd). The process's main thread supervises: it hears the worker die (`ERR_WORKER_OUT_OF_MEMORY` is `snippet.memory`) and runs a watchdog that reports a worker busy past guardMs + 10 s with no ctx call as stuck (`snippet.timeout_guard`). Why: review round 1 found that `resourceLimits` only recovers V8's near-heap-limit path. A growing Map or object, or one huge allocation, makes V8 call FatalProcessOutOfMemory, which aborts every thread in the process. Now that abort ends only the snippet process. Main reads EOF and matches the process's stderr (an unlinked temp file) against V8's out-of-memory messages to report `snippet.memory`. Reversible: yes.
- ctx calls cross synchronously over two FIFOs (`mkfifo` in a temp dir that is removed once both ends are open). Main and the worker use blocking `readSync`/`writeSync`, one frame per message: a 4-byte length, then `v8.serialize` output. The worker writes `{seq, id, args}` and blocks until main replies. Calls carry a sequence number and the worker drops stale replies. Before a ctx call writes anything, the worker recurses 400 frames to check it has stack to spare, so a snippet at the stack limit gets its RangeError before a frame starts and a frame is never cut. Main opens each FIFO first by an end that does not block (O_RDWR, O_RDONLY|O_NONBLOCK) and waits up to 10 s for a hello byte, so a process that never starts cannot hang main. A round trip costs about 9 microseconds, so 20 000 ctx calls fit well inside guardMs. Why: snippet semantics stay synchronous across a process boundary. Reversible: yes.
- ctx stays on main. ctx and every value a ctx member returns are encoded as plain data with each function replaced by a placeholder object listed beside the value (structured clone keeps identity within one message); the worker turns placeholders into counted wrappers. Host errors stay on main and cross as id, message, name and own primitive fields; a copy that escapes the run maps back to the original. The quota is counted in the worker, per run. Symbols in ctx data become `undefined`; a symbol in a ctx argument or result is refused as not plain data. Why: same copying contract as engine-sandbox, now across a thread. Reversible: yes.
- Snippet processes are pooled per heap limit at module level (idle cap 4) and reused across runs and hosts. They start lazily, run eval code with `execArgv: []` (no tsx), and are unref'd. When main closes the FIFOs or exits, the worker reads EOF and the process exits. A nested run (a ctx member on main that runs another snippet, e.g. handler snippets behind a client's `ctx.api`) is sent to the same process. Its worker serves that request inside the ctx call it is blocked on, with a fresh realm, as the in-process vm did. So nesting never waits for a process to start inside the outer snippet's wall-clock guard. That wait made `npm run check` flaky under load before this change. If the nested run kills the process (out of memory), every run waiting on it gets the same fault. `snippetWorkersStarted()` counts started processes for tests. Why: a process plus its worker starts in about 130 ms. A run on a warm one costs a fresh realm plus a pipe round trip. A per-host pool would leak processes per `createVmHost`. Reversible: yes.
- The worker never turns its event loop (it loops on a synchronous receive), so snippet Promise rejections never reach any process listener. The promise hook still faults any run that creates a Promise (`snippet.promise_returned`). The engine-sandbox rejection filter and the guarded `silence` pass are removed. Reversible: yes.
- Arrays passed to ctx members or returned from snippets are copied by index (`length`, then one descriptor per index). Holes stay holes, and named properties on an array are not copied. Why: listing the names of a 3-million-element array inside the 128 MB worker heap ran out of memory on a snippet that is not runaway (review round 1). A getter at an index is still refused. Reversible: yes.
