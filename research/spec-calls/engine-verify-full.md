# Spec calls: engine-verify-full

- A successful write is a call below 400 that committed a row change, found as a call entry in the run's journal at the call's engine time. It is not defined by HTTP method. Why: a GET action can change rows, and a successful POST can change none. A tick of at least 1s means no two successful calls share a time, so the match is exact. Reversible: yes.
- Strict prefixes are k = 1 .. n-1 writes. The empty prefix is the noop gate, so `bestPrefixScore` is null when the solution has at most one write. Why: acceptance 3 says null for one write. Reversible: yes.
- Prefixes are replayed in one pass on one runtime from seed, not in one run per prefix. The pass re-issues every successful call of the first solution log, reads included, so engine time and job firings match the original run. Refused calls are skipped because they changed nothing. Each state right after write k is graded. Why: cost stays linear in the solution's calls, and the prefix state is exactly the solution's state at that point. Reversible: yes.
- Only the shortest prefix that scores 1 is reported as task.prefix_full_marks, at ['tasks', id]. The scan stops there. Why: one fix covers the rest. Either the grader ignores later work or the solution makes a needless write, so the path is the task and not the grader. Reversible: yes.
- Prefixes are checked only when the solution scores exactly 1. Decoys run only when the grader graded the solution without a fault. Why: a prefix that beats a below-1 solution would make the hint "the grader ignores the rest of the work" wrong. A grader that faults on the solution would fault again on each decoy. Reversible: yes.
- same_as_noop and same_as_solution compare state content: rows without created_at and updated_at, no id counters, no clock. Why: a decoy that writes and then undoes the change, or that reaches the solution's rows through different reads, differs from noop or the solution only in timestamps. Equal state hashes imply equal content, so the acceptance's state-hash cases are still caught. Reversible: yes.
- Each decoy reports at most one issue: run failure, grader fault, trivial (checked in the order no_successful_write, same_as_noop, same_as_solution), or full marks. A trivial decoy at full marks is reported as trivial. Why: a decoy that equals the solution says nothing about the grader, so the decoy is what needs fixing. Reversible: yes.
- A decoy that throws or fails its own assert yields snippet.runtime_error at ['tasks', id, 'decoys', i, 'script']. task.decoy_required sits at ['tasks', id, 'decoys']. Trivial and full-marks issues sit at ['tasks', id, 'decoys', i]. Reversible: yes.
- A 5xx in the reference solution's log reuses snippet.runtime_error. It sits at ['actions', a, 'handler'] when action a answered, and at the solution path otherwise. Only the first 5xx per endpoint is reported, and it is reported even when the solution run then fails, before that run's issue. Why: the design doc's proof table fails such a run. The handler is the snippet that broke, and owner at_path sends the repair to the actions stage. No new catalog code is needed. Reversible: yes. A dedicated code such as `task.reference_server_error` would make the expected text more exact.
- Decoy runs are not checked for 5xx. Why: the unit names reference runs only. A decoy that crashes a handler would point at a real world bug, so this is a candidate to add. Reversible: yes.
- Identical issues (same code, path and found) are kept once across solution, noop, prefix and decoy grading. Why: one grader fault is one fix. This generalizes the basic unit's solution and noop dedupe. Reversible: yes.
