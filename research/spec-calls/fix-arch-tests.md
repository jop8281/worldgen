# Spec calls: fix-arch-tests (YOS-64)

- **SC-1. The engine boundary covers every src file outside `src/engine/`.** That means worldgen, cli, lib and files directly under src. A src/lib file that imports or re-exports an engine internal is itself reported. Why: Acceptance 1 says src/lib bridged worldgen to engine internals unseen. Reversible: yes.
- **SC-2. Re-export chains are followed name by name.** The edges are `export * from`, `export * as ns from`, `export { a as b } from`, and an imported binding exported again by a local `export { a }`, by `export default a`, or by `export const b = a` (a bare imported identifier, parentheses aside). An importer is reported only when a name it imports arrives at the forbidden file, and that file really exports the name. So importing `own` from a module that also re-exports engine internals does not fire, but that module does. Chains that enter the engine through `#engine` pass. Bridges outside src, such as test/helpers, are followed. A value bridge that names an imported binding is followed like a re-export. Names are resolved with the TypeChecker, so the bridge may be `export const m = anthropicModel`, `export default anthropicModel`, a local alias (`const alias = anthropicModel; export { alias }`), a member of a namespace import (`export const m = llm.anthropicModel`), or any of these wrapped in parentheses, `as`, `satisfies` or `!`. Local variables are followed whether declared const, let or var, which can only over-report. One that computes a new value from it (`export const m = wrap(anthropicModel)`, `anthropicModel + 1`) is not. Why: Acceptances 1 and 2 ask for re-exports, and the name-by-name check keeps unrelated imports quiet. Reversible: yes.
- **SC-3. A re-export path to llm.ts is allowed only for model-free data types (`Usage`) when the path is type-only.** This matches the direct-import exemption. Why: a type-only `Usage` carries no model. Reversible: yes.
- **SC-4. The SDK rule and the new model routes are one rule, `modelConfinement`.** Outside `src/worldgen/llm.ts` it reports four things: an SDK import; any string literal `child_process` or `node:child_process` (so import, require, `process.getBuiltinModule` and dynamic import all fire); a spawn, exec, execFile or fork call (or execa) whose command is the `claude` binary, bare or by path, as a literal or a template head; and any string or template part containing `api.anthropic.com`. SDK imports are listed first as `<file> -> <specifier>`, then the routes as `<file>:<line> <what>`. Why: Acceptance 3. Under U-11 (A-56) the `claude -p` transport is the model client, so it belongs in llm.ts. Reversible: yes. This also bans child_process in cli/ and engine. A future `cli/eval.ts` that spawns runs needs the rule changed in the same commit.
- **SC-5. A brand is forged without `as Brand` in two ways, and both are reported outside the owner.** The first is an `as any` or `<any>` whose contextual type carries a brand (`any to CheckedWorld`). The second is a generic call or `new` whose result carries a brand that neither the callee's declared result (before type arguments apply) nor the type of any argument the call actually passes already carries (`generic cast to CheckIssue`). The callee must be a generic function or method, or for `new` a generic class declared in project source. One test covers every route: an explicit type argument with an `unknown` parameter, an inferred return (`return { v: x as T }`), a class (`new Box<CheckIssue>(x)` fires at the `new`; the later `.get()` does not), an unpassed optional parameter (`hinted<CheckIssue>(x)`), `Partial<T>` (`fill<CheckIssue>({ code: 'x' })`) and a union (`orStr<CheckIssue>('x')`). A call that passes a branded value through, like `first(issues)`, `new Holder(issue)` or `orStr(issue)`, does not fire, and neither does a generic whose declared result names the brand itself. Library classes are trusted, so `new Map<string, CheckIssue>()` (an empty container) does not fire. Library functions are checked like project ones, so `z.custom<CheckIssue>()` fires: it returns T from no input (review round 5). An `as never` (or `x as unknown as never`) is judged like `as any`, by the contextual types its value reaches, because never is assignable to every brand (review round 5). This replaces the earlier type-parameter-supply test, which a parameter typed `Partial<T>` or `T | string` slipped past (review round 4). Why: Acceptance 4. Reversible: yes.
- **SC-6. Spec: a bare `as unknown` cannot reach a branded slot.** `unknown` is not assignable to a brand, and `CheckIssue | unknown` collapses to `unknown`. So `as unknown` forging always needs a second assertion, which the `as Brand` check catches, or a generic, which SC-5 catches. The rule still checks `as unknown` against the contextual type, but no well-typed fixture can trigger it. An `as any` / `as unknown` that initializes or is assigned to a variable typed any or unknown is followed through every read of that variable, transitively and across src files, and each read's contextual type is checked too (`const x = {} as any; const w: CheckedWorld = x;` fires at the cast). The forge is reported once, at the cast. An `any` that does not come from a cast, such as `JSON.parse`, is not checked, and a cast value stored in an object or array property is not followed. Reversible: yes.
- **SC-7. A `default:` clause must end on the assertNever call, and nothing before it may leave the clause.** It passes only when its last statement, with blocks opened, is `return assertNever(x)`, `throw assertNever(x)` or `assertNever(x);`. No earlier statement may contain a return, a throw, a labeled break or continue, or a break or continue not owned by a nested loop or switch. A call inside a conditional, after a return, or in a ternary fires. The call's one argument must be a plain reference (`k`, `o.k`, `e`) whose declared type is not never, so its never type comes from the switch narrowing it: `assertNever(k as never)`, `assertNever(<never>k)` and a variable declared never all fire. This replaces SC-9 of infra-architecture-symbols ("calls assertNever somewhere in its body"). Why: Acceptance 5. Reversible: yes.
- **SC-8. Engine core also bans `Function`, `eval` and `Intl`, in type and value positions like `Date`.** It also bans every read of `.constructor` or `['constructor']` whose member is declared only in a library declaration file, or whose receiver is `any`, read by property access, element access or object destructuring (`const { constructor: F } = () => 0`, shorthand, quoted key or an `any` parameter pattern). A constructor property declared in project source does not fire. Why: Acceptance 6. `(() => 0).constructor` is the Function constructor and `Intl.DateTimeFormat` reads the host clock and zone. Reversible: yes.
- **SC-9. Real-tree findings: none.** Every rule, old and new, returns `[]` on the real tree at the integration base. No src file changed. Reversible: n/a.
