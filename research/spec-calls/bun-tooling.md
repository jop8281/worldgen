# Spec calls: bun-tooling

- `bun.lock` replaces `code/package-lock.json`; it is the only lockfile, and CI installs with `bun install --frozen-lockfile`. Why: one package manager, and a frozen install catches a stale lock. Reversible: yes.
- `tsx` stays a devDependency. Why: `test/cli-world.test.ts` spawns `node --import tsx src/cli/worldplay.ts` and `test/sandbox.test.ts` spawns `process.execPath --import tsx`, and `test:node` needs it. Drop it once those tests spawn `bun` and the Node job goes. Reversible: yes.
- Scripts `worldplay`, `worldgen`, `eval` and `docs` run `bun src/cli/<name>.ts`. `bun run <script> args` forwards args with or without `--`, so the docs drop the `--`. Reversible: yes.
- `typecheck` stays `tsc -p tsconfig.json && tsc -p tsconfig.engine-core.json`; `bun run` puts `node_modules/.bin` on PATH, so no `bunx` is needed. The tsconfigs keep `types: ["node"]` and add no Bun types. Why: the code imports `node:*` modules, which Bun implements, and nothing calls `Bun.*`. Reversible: yes.
- `test` is `bun test --timeout 120000 ./test`. Why: Bun's default per-test timeout is 5 s, while node:test has none; `rule: engine core references no banned global > passes on the real source tree` took 7.9 s under load and timed out. `./test` keeps discovery to `code/test/`, as the old `test/*.test.ts` glob did. Reversible: yes.
- `test:node` (`node --import tsx --test test/*.test.ts`) is kept. Why: the spike makes Node the green gate until bun-sandbox-compat lands; it costs one script line. Reversible: yes, delete it with the Node CI job.
- `check` is `bun run typecheck && bun run test`, so it uses the `test` script's flags. Reversible: yes.
- `engines` lists `bun >=1.4` and keeps `node >=22`. Why: Node still runs `test:node` and the spawned CLI tests. Reversible: yes.
- CI: the required job `check` uses `oven-sh/setup-bun@v2` with `bun-version: 1.4.x`, then `bun install --frozen-lockfile` and `bun run check`. A second job `node` (`continue-on-error: true`) installs with Bun, sets up Node 22 and runs `bun run typecheck` and `bun run test:node`. Why: the unit spec makes Bun the required job; the spike suggested the reverse, so the Node job keeps the full suite visible while `check` is red on the 9 known sandbox failures. Reversible: yes.
- The session hook installs Bun with the official script only when `bun` is missing from PATH and `$BUN_INSTALL/bin` (default `~/.bun/bin`), appends that bin dir to `CLAUDE_ENV_FILE` when set, then runs `bun install` in `code/`. It stays a no-op outside remote sessions. Reversible: yes.
- `code/README.md` is not created. Why: README.md and AGENTS.md already carry the commands, and a third copy would drift. Reversible: yes.
- Known Bun failures, all one cause at the root: `src/engine/sandbox.ts` calls `promiseHooks.onInit` from `node:v8`, which Bun 1.4.2 throws on ("node:v8 onInit is not yet implemented in Bun"). It increments `promiseHookDepth` before the call, so only the first guarded call in a process faults, and every later call runs without promise tracking. Under `bun test` all files share one process, so the first snippet call fails in whichever file runs first: `compile > compiles a function expression whose run returns ctx.now()` here, and `check: references layer > allows the same path with a different method` in the spike and when `check.test.ts` runs alone. The other 8 are the spike's `sandbox.test.ts` list. Owner: bun-sandbox-compat. Reversible: n/a.
