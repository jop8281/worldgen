# Spec calls: fix-engine-store (YOS-68)

- Both findings reproduced at base 60c03cb. P1: `create` with an omitted `name: {type: string}` (not required, not nullable, no default) stored `name: null`, and `update({name: null})` was then refused `field.null`. P2: unique datetime accepted both '2026-01-01T00:00:00Z' and '2026-01-01T00:00:00.000Z'.
- Acceptance 1, store-no-key vs refuse: chose store-no-key. Creating a row that omits a non-required, non-nullable field without default stores no own key for it. A nullable field still stores null, and a required field is still refused `field.required`. Why: refusing would make `required: false` meaningless for non-nullable fields without a default. Readers (api sort and filter, rowDiff, stateHash) already read a missing key as null. `tx.list` (the reader snippets use) did not: it compared `r[k] === where[k]`, so `where: {field: null}` missed rows with the key omitted. Review round 1 fixed it to read `r[k] ?? null`. Reversible: yes.
- Acceptance 2, canonical datetime: `FIELD_TYPES.datetime.validate` returns `YYYY-MM-DDTHH:mm:ss.sssZ`, always with 3 fraction digits. Digits past 3 are kept only up to the last non-zero one, so sub-millisecond instants stay distinct and no precision is lost. For millisecond instants the form matches `toIso()`. Every store write of a datetime goes through validate, so this covers user fields and privileged `created_at`/`updated_at` writes, and unique compares instants. No Date is used. Reversible: yes.
- `parseQuery` for datetime still returns the raw string, because query filters compare through `compare`, which normalizes. The existing fields test pins this.
- Consequence: a world that seeds datetimes without a fraction ('...00Z') now stores '...00.000Z', so its state hash changes. No checked-in world or test pinned the old form (`npm run check` green).
- Review round 1, `tx.list` where on canonical datetimes (U-5, model-written snippets): once datetimes are stored canonical, a raw `===` filter missed rows when a snippet passed the literal it wrote ('...00Z'). `tx.list` now passes each where value of a declared field (and of `created_at`/`updated_at`, as datetimes) through that field's `validate` and compares the result with `===`. A value the field refuses stays raw and matches nothing, so where keeps strict-equality semantics (where `{size: '5'}` does not match int 5). Chosen over `compare(...) === 0` because the number kinds' compare returns 0 for NaN and would let a refused value match every row. Reversible: yes.
