# Build worlds that prove their own graders

Research already contains the blueprint for both halves of this project, and what is left is engineering discipline rather than invention. The closest prior art to WorldGen is Snowflake's **Agent World Model (AWM)**. It turned seed domains into **1,000 executable, SQLite-backed, MCP-exposed worlds at about $0.57 each**. Its pipeline is staged (scenario → tasks → schema → seed data → tool spec → code → verifier) and every stage repairs itself against runtime errors. Agents trained only on those worlds improved on out-of-distribution benchmarks ([arXiv 2602.10090](https://arxiv.org/html/2602.10090)). The engine side has a clean template in Sierra's τ²-bench: a typed JSON database, Python tools, a policy file, and grading by replaying a reference solution on a fresh copy and comparing end states ([tau2-bench](https://github.com/sierra-research/tau2-bench)). The hard part is trust in the grader, not world code. Audits find **evaluators disagree with human experts on 18.5% of tool-calling tasks** ([arXiv 2607.02577](https://arxiv.org/abs/2607.02577)). AWM itself reports that **74% of generated worlds contain at least one bug** ([arXiv 2602.10090](https://arxiv.org/html/2602.10090)). No commercial vendor was found shipping a general "description → graded stateful replica" product. Vendors hand-build replicas that cost roughly **$20k for a website clone and $300k for a Slack-class product** ([Epoch AI](https://epoch.ai/gradient-updates/state-of-rl-envs)), so the opening is real. The recommended build is a deterministic engine that owns state, reset and grading, with graders that must show, under probes, that they discriminate before a world counts as passing. WorldGen then becomes a tasks-first staged generator whose repair loop runs on the engine's structured errors. browser-use fits only as an optional agent harness for a UI layer, not as part of the engine.

## A converged recipe exists in papers, but nobody sells it

From 2024 to 2026 the field moved from "an LLM writes configs for an existing simulator" to "a coding agent writes an entire database-backed world plus tasks plus verifiers." EnvGen (2024) only generated configurations for Crafter ([arXiv 2403.12014](https://arxiv.org/abs/2403.12014)). By 2026, AWM, EnvScaler, AgentScaler and DeepSeek-V3.2's environment-synthesis agent all followed the same shape: **seed → scenario → tasks → database schema and seed data → tool code → verifier → execution-driven repair → solvability filter**. DeepSeek-V3.2 built **1,827 environments** this way. Its key rule is that the reference "solution function is restricted to invoking tool functions … cannot … directly access the database," and only tasks with non-zero pass@100 are kept ([arXiv 2512.02556](https://arxiv.org/html/2512.02556)). WorldGen would be productizing a design the research community has already agreed on. That makes its main risk execution quality, not concept risk.

The table below covers the works that matter most to this project.

The commercial market is large and still mostly hand-built. Epoch's interviews price tasks at **$200–$2,000** each. One interviewee complained that "what everyone does is vibe code a buggy website which isn't useful" ([Epoch AI](https://epoch.ai/gradient-updates/state-of-rl-envs)). Mercor describes environments as worlds plus "high-fidelity app clones (Salesforce, ServiceNow, Microsoft 365)" plus verified tasks, with labs buying about **50,000 tasks a month** ([Sequoia podcast](https://sequoiacap.com/podcast/how-rl-environments-are-built-and-why-they-re-your-ai-moat)). Turing packages each replica as "a Docker container with APIs for task retrieval, reset, and verifier-based scoring," and that is the same contract this engine needs ([Turing](https://www.turing.com/frontier-ai/rl-environments)). Vendors that claim generation use it for *content inside* hand-built apps. Halluminate's Westworld, for example, uses procedurally generated data in deterministic, resettable app clones ([Starlog](https://starlog.is/articles/developer-tools/halluminate-westworld)). The searches found no company matching the "worlds … WorldGen" description. The name "WorldGen" belongs publicly to Meta's text-to-3D scene system ([arXiv 2511.16825](https://arxiv.org/abs/2511.16825)), which is unrelated. The skeptics' case deserves weight too. Ross Taylor warned that "even the best publicly available [environments] typically don't work without serious modification" ([TechCrunch](https://techcrunch.com/2025/09/21/silicon-valley-bets-big-on-environments-to-train-ai-agents/)). An ICML 2026 talk argued that human-designed simulators are "gameable by construction" ([ICML 2026](https://icml.cc/virtual/2026/78363)). Both points lead to the same conclusion: a generator is only credible if it ships verified graders.

## Code-backed state beats LLM-simulated state by a wide margin

Before designing the engine, decide whether worlds should be executable code and data or an LLM pretending to be the API. The evidence favors executable state for anything graded. EnvSimBench gave seven frontier models a pre-state and a tool call and asked them to produce the post-state. They got **97–100% right on read-only operations, but only 22–50% on single-field writes and ≤4% on writes touching five or more fields**. In 50–64% of multi-field failures the model produced plausible feedback while silently corrupting state ([arXiv 2605.07247](https://arxiv.org/html/2605.07247)). In AWM's head-to-head RL comparison, code worlds beat a GPT-5-simulated environment on BFCLv3 (**65.94 vs 52.53**) and MCP-Universe (11.17 vs 6.15). On τ²-bench the simulator came close (31.30 vs 33.45) ([arXiv 2602.10090](https://arxiv.org/html/2602.10090)). The older ToolEmu work also found that **about 31% of failures flagged in its LLM-emulated sandbox were emulator artifacts** rather than real agent failures ([arXiv 2309.15817](https://arxiv.org/abs/2309.15817)).

Simulation has a real case, and the strongest version deserves a fair statement. Simia trained Qwen2.5-32B entirely on LLM-simulated tool feedback and beat GPT-4o on τ² Airline and Retail ([arXiv 2511.01824](https://arxiv.org/html/2511.01824)). Kimi K2 generated SFT data across **20,000+ synthetic tools** with a stateful LLM world model ([arXiv 2507.20534](https://arxiv.org/html/2507.20534)). Across Kimi K2, GLM-4.5, DeepSeek-V3.2 and AWM, the pattern is that simulation is used for breadth of training data, while code is used where a reward depends on state. For a product whose whole point is "a grader reads the end state," the database must be the source of truth. An LLM fits in three narrower places: generating realistic free-text content, playing a simulated user, and at most a CompoWorld-style fallback for long-tail tools ([arXiv 2609.33665](https://arxiv.org/abs/2609.33665)). When the LLM does touch state, EnvSimBench's "constraint-driven simulation" (pre-state, implementation code and typed state-change operations) is the way to ground it.

The classic API-mocking ecosystem confirms the gap rather than filling it. Prism and stripe-mock are explicitly stateless; stripe-mock says it validates POSTs and then ignores the data ([stripe-mock](https://github.com/stripe/stripe-mock)). WireMock Scenarios and Hoverfly support only global finite-state machines ([WireMock](https://wiremock.org/docs/stateful-behaviour/)). json-server and Mockoon give generic CRUD with no business rules ([json-server](https://github.com/typicode/json-server)). Only hand-written emulators carry domain invariants such as cascades, webhooks and token rotation; examples are moto and vercel-labs/emulate, which emulates Stripe, GitHub, Slack and others from in-memory typed collections seeded from YAML ([vercel-labs/emulate](https://github.com/vercel-labs/emulate)). **No mocking tool derives business-logic state transitions from a spec automatically.** That is exactly the layer WorldGen has to produce.

## The engine should own state, time, reset and grading

### State, determinism and reset

τ²-bench shows how small a world engine can be. State is a Pydantic `DB` loaded from `db.json` with a canonical hash. Tools are flagged as mutating or read-only, and agent and user toolkits keep separate databases to model "dual control." The evaluator rebuilds the agent's end state by replaying its trajectory. It builds a gold state by replaying the task's reference actions on a fresh copy, then compares the two ([evaluator_env.py](https://github.com/sierra-research/tau2-bench/blob/main/src/tau2/evaluator/evaluator_env.py)). The reference actions are "**one** reference trajectory … not the only correct one." They exist because the target state "is easier to express as 'play these actions on a fresh env' than to spell out by hand" ([docs/evaluation.md](https://github.com/sierra-research/tau2-bench/blob/main/docs/evaluation.md)). That idea is what keeps generated tasks cheap: WorldGen writes a reference solution, and the engine computes the expected state.

AppWorld adds two determinism techniques that a whole-DB hash needs. It **freezes the clock per task**, and it stores task variations as diffs over a base SQLite database, with `save_state`/`load_state` checkpoints ([AppWorld repo](https://github.com/StonyBrookNLP/appworld)). A τ-style hash fails on harmless differences (timestamps, auto-generated IDs) unless the world is fully deterministic. The engine should therefore use a virtual clock that advances only on committed writes, seeded per-entity ID counters, integer money and canonical JSON, plus a CI test that runs reset → reference twice and checks the hash is identical. The user's plan already specifies all of these, so this is a confirmation, not a change.

Reset cost determines whether pass^k and RL are affordable, and the options form a clear ladder. A WebArena shopping container needs **about 6 GB and about one minute to start** ([arXiv 2510.16252](https://arxiv.org/abs/2510.16252)). OSWorld-Verified needed AWS fan-out to cut full evaluation "from 10+ hours to minutes" ([xlang.ai](https://xlang.ai/blog/osworld-verified)). At the other end, REAL keeps clone state in browser localStorage, so reset costs essentially nothing, though grading then needs a `/finish` submission ([arXiv 2504.11543](https://arxiv.org/pdf/2504.11543v1)). An **in-process SQLite (or `:memory:`) store, restored through the backup API**, sits near the cheap end while keeping server-side state the grader can read. AWM shows the scale this enables, with **1,024 parallel world instances per RL step** ([arXiv 2602.10090](https://arxiv.org/html/2602.10090)). SQLite also gives real transactions plus FK/UNIQUE/CHECK constraints as a backstop. That matters because database-constraint conflicts were **14% of AWM's residual bugs** ([arXiv 2602.10090](https://arxiv.org/html/2602.10090v3)). No source benchmarked SQLite reset latency directly, so the "milliseconds" claim is an inference from the design rather than a measured figure.

### World spec format: declarative where possible, code where not

The research leans toward a typed, declarative intermediate representation that the engine checks, with generated imperative code kept to a minimum. Text2World found that validator feedback raised executability of generated PDDL worlds from **72.3% to 89.1% in three rounds, but semantic errors such as missing preconditions and effects persisted** ([arXiv 2502.13092](https://arxiv.org/html/2502.13092v1)). AWM states the same limit: "self-correction primarily addresses runtime errors, not logical inconsistencies," and **44% of its bugs were unhandled edge cases** such as missing null and boundary checks ([arXiv 2602.10090](https://arxiv.org/html/2602.10090v3)). A declarative format with enums, refs, state machines with guards and effects, and statically type-checked expressions moves that whole class of bugs into the engine, where one well-tested implementation enforces it for every world. WorldSeed is an open example: worlds are defined "entirely in YAML," the rule engine resolves deterministically, and an LLM "Dungeon Master" handles only ambiguous outcomes ([WorldSeed](https://github.com/AIScientists-Dev/WorldSeed)). AutoEnv also routes generation through a three-layer YAML DSL ([arXiv 2511.19304](https://arxiv.org/html/2511.19304)). The counter-argument is expressiveness. AWM, EnvScaler and DeepSeek all generate Python and reach ~2,000-LOC worlds, which suggests no declarative DSL will cover every business rule. **No controlled study compares DSL against Python as the generation target**, so this is a judgment call. The defensible position is to go declarative-first, measure which requested behaviors the DSL cannot express, and add a sandboxed code escape hatch only when that list is non-trivial.

A concrete world spec, consistent with these precedents and with the user's plan, is a directory with these parts:

- a manifest (id, version, clock start, RNG seed, auth style, pagination style);
- a data model (entities, typed fields, refs with on-delete behavior, uniqueness, checks);
- an API surface (routes mapped to CRUD or named actions);
- logic (per-entity state machines, actions as input → guards → effects, timers);
- a seed generator spec plus a locked materialized seed;
- tasks.

Statecharts express per-entity lifecycles naturally (ticket: new → open → escalated → resolved). Gherkin's Given/When/Then maps directly onto seed state → agent action → verifier assertion. The notes found no published work using either for LLM environment generation, so these are format suggestions rather than proven practice.

### API exposure: HTTP with OpenAPI first, MCP generated from it

The frameworks agree on a contract. Harbor, verifiers v1, HUD, ORS, NeMo Gym and OpenEnv all reduce to the same parts:

- a task spec (id, instruction, split);
- a world runtime (a container image or a stateful session);
- actions exposed as tools;
- a `grade` hook that returns a scalar plus named sub-scores;
- setup and teardown lifecycle hooks;
- a trace record.

MCP has become the default way to expose tools. verifiers installs Toolsets "as MCP servers into the harnesses," HUD has an `mcp` capability, OpenEnv has an MCP RFC, and AppWorld now serves all 457 APIs over MCP ([verifiers](https://github.com/PrimeIntellect-ai/verifiers/blob/main/docs/v1/overview.md); [HUD](https://github.com/hud-evals/hud-python); [OpenEnv](https://github.com/meta-pytorch/OpenEnv); [AppWorld](https://github.com/StonyBrookNLP/appworld)). AWM's generated worlds are FastAPI apps that also expose MCP ([Snowflake blog](https://www.snowflake.com/en/blog/engineering/agent-world-model-for-agentic-reinforment-learning/)). The recommendation is to make **REST with an engine-generated `/openapi.json` the canonical surface**, because it replicates "real software" and lets Schemathesis-style tooling test it. An MCP server (one tool per route, schemas taken from the OpenAPI) should be derived from it automatically. A separate admin plane (reset, state, diff, clock, grade, hash) on its own port keeps those controls out of the agent's reach. METR found reward hacking was **43 times more common when models could see the scoring function** ([METR](https://metr.org/blog/2025-06-05-recent-reward-hacking)). Harbor and verifiers both now run verifiers in a separate sandbox and pass over only declared artifacts ([Harbor verifier](https://docs.harborframework.com/tasks/verifier.md); [verifiers v1 env](https://github.com/PrimeIntellect-ai/verifiers/blob/main/docs/v1/env.md)). For adoption, a Harbor task-directory export and a Gym-style `reset/step` adapter reach the most training stacks, since SkyRL, verifiers, NeMo Gym and OpenEnv all consume Harbor tasks ([SkyRL](https://github.com/NovaSky-AI/SkyRL); [NeMo Gym](https://github.com/NVIDIA-NeMo/Gym)).

## Graders are the product, and they must show they discriminate

### Every grading style fails in a known way

Evaluator error is about as large as the gaps between leading agents. The 2026 validity audit of BFCL v4, τ²-Bench, LiveMCPBench and MCP-Atlas found **92 evaluator–human disagreements in 496 tasks (18.5%)**. Deterministic graders failed through "brittle state matching, trajectory lock-in, incorrect ground truths, substring-based communication failures." LLM judges failed through "rubric drift, hallucinated completion … substantial run-to-run variance." One LiveMCPBench setup ranged **from 57.9% to 76.8% across 23 repeated evaluations** ([arXiv 2607.02577](https://arxiv.org/abs/2607.02577)). Among FAIL verdicts on computer-use benchmarks, **15.3% were wrong** ([arXiv 2607.28367](https://arxiv.org/abs/2607.28367)). The ABC checklist found a do-nothing agent **passed 38% of τ-bench airline tasks** ([Kang/ABC](https://ddkang.substack.com/p/ai-agent-benchmarks-are-broken)), and τ³ needed "75+ fixes" for wrong actions and impossible constraints ([tau2-bench](https://github.com/sierra-research/tau2-bench)). The problem is concentrated in task data, and a generator will produce task data at a volume no human can audit. So validation has to be automatic and adversarial.

### A layered score vector

The design that fits the evidence is a score vector built from parts with different failure modes. The core is an **end-state diff against the gold state derived from the reference**, not a hash, with volatile fields normalized. It is paired with an **allow-list of expected mutations and a collateral gate**: AppWorld's "checking for unexpected changes, i.e., collateral damage" ([arXiv 2407.18901](https://arxiv.org/abs/2407.18901)). **Forbidden-state assertions** follow ToolSandbox's minefields, whose guardrail similarity returns 0 on mismatch ([ToolSandbox](https://github.com/apple/ToolSandbox)). They catch "refund twice" or "deleted the customer." Partial credit comes from weighted checks. Anthropic's example is that a support agent that verifies the customer but fails to refund "is meaningfully better than one that fails immediately" ([Anthropic](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)). Trajectory matching should stay out of the reward, except for policy checks the end state cannot show. Sierra keeps `ACTION` out of the default reward basis, and Anthropic warns against requiring "a sequence of tool calls in the right order" ([τ² docs](https://github.com/sierra-research/tau2-bench/blob/main/docs/evaluation.md); [Anthropic](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)).

LLM judges belong in a separate, labelled metric for unstructured deliverables. They should use checklist rubrics, because Rubrics-as-Rewards beat Likert judges by **up to 31% relative** ([arXiv 2507.17746](https://arxiv.org/abs/2507.17746)). Where possible they should be agentic judges that inspect artifacts, since Agent-as-a-Judge reached **about 90% human agreement versus 60–70%** for one-shot LLM judges ([arXiv 2410.10934](https://arxiv.org/abs/2410.10934)). AWM's hybrid result points the same way: a code-augmented judge that reads DB diffs beat both code-only and LLM-only rewards (**65.94 vs 60.00 vs 55.46 on BFCLv3**). It still had a **9.2% reward flip rate** ([arXiv 2602.10090](https://arxiv.org/html/2602.10090)), which is why it should supplement deterministic checks rather than replace them. Report **pass^k** alongside pass@k: at 75% per-trial success, pass^3 is only about 42% ([Anthropic](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents); [arXiv 2406.12045](https://arxiv.org/abs/2406.12045)).

### Graders must pass a gauntlet before a world counts

The most useful finding for WorldGen is how to validate a generated grader automatically. τ²-bench's compositional generator gives each sub-task init, solution and assertion functions. Correctness is "automatically verified by checking if the final state satisfies all assertion functions after applying initialization and then solution functions," and composite tasks are checked to stay unsolved until every solution step runs ([arXiv 2506.07982](https://arxiv.org/html/2506.07982)). WorkArena's `cheat` oracle per task gives the same guarantee and also produces training traces ([arXiv 2407.05291](https://arxiv.org/abs/2407.05291)). Mutation testing closes the loop. GameLogicBench requires evaluators to reject "implementations with one required capability removed," and reports that "without this validation, incorrect agent submissions passed" ([arXiv 2609.21562](https://arxiv.org/abs/2609.21562)). A gold-sanity gate flagged **61.9% of LLM-generated tests as failing on the gold solution itself**, which an LLM judge alone missed ([arXiv 2606.16062](https://arxiv.org/pdf/2606.16062)). In code RL environments without such gates, **wrong patches passed 25–28.5% of the time** ([arXiv 2606.16062](https://arxiv.org/pdf/2606.16062)). The engine should therefore run a fixed gauntlet on every task:

- the reference scores 1;
- a no-op scores 0 (this kills the τ-bench "do-nothing passes" bug);
- every strict prefix of the reference scores below 1;
- engine-generated mutants fail (wrong target entity, an extra destructive write, a policy-violating shortcut, a confident no-op);
- a valid alternative solution scores 1, where one exists;
- two identical runs hash identically.

Mutants must come from the engine, not the LLM, because a model writing both the grader and its "decoys" is grading itself. Finally, run N agent attempts. Treat 0% as a likely broken task, following Anthropic's rule that "0% pass rate across many trials is most often a signal of a broken task" ([Anthropic](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)). Treat 100% as too easy. Epoch puts a useful RL floor at roughly 2–3% pass rate ([Epoch AI](https://epoch.ai/gradient-updates/state-of-rl-envs)).

## WorldGen should generate tasks first and repair on grounded errors

### Stage order and what each stage emits

Generation order matters. AWM generates **tasks before the schema**, so tables exist only when a task needs them and seed rows come from task preconditions. Its audit found **11.5% blocked tasks versus 46.8% for env-first EnvScaler** on its sample, and **task feasibility of 3.99/5 versus 3.14** ([arXiv 2602.10090](https://arxiv.org/html/2602.10090)). That is one paper using its own judge, so it needs replication, but it agrees with DeepSeek-V3.2's design and with the Verified Synthetic Web Environments result. In that work, feasible tasks rose from **48.6% raw to 94.8% after verification**, which means about half of naively generated environments are unusable ([arXiv 2608.21898](https://arxiv.org/abs/2608.21898)). Typed artifacts at each stage boundary limit cascading hallucination. MetaGPT's PRD → design → API chain and AlphaCodium's YAML-structured flow both rely on this ([arXiv 2308.00352](https://arxiv.org/abs/2308.00352); [arXiv 2401.08500](https://arxiv.org/abs/2401.08500)).

| Stage | Output | Engine gate (error returned to WorldGen) |
|---|---|---|
| 0. Normalize | Structured plan: entities, actors, flows, invariants, open questions with default answers | Schema-valid; every flow references known entities |
| 1. Tasks | NL instructions with structured preconditions and expected effects | Schema-valid; each task maps to at least one flow |
| 2. Data model | Typed entities, refs, constraints | DDL compiles; every precondition maps to fields; no orphan tables |
| 3. API + logic | Routes, state machines, guards, effects, timers | Expressions type-check; every task reachable via declared routes; inline-fixture scenario tests pass |
| 4. Seed | Generator spec → locked rows | FK, unique, enum and check constraints pass; all task preconditions hold |
| 5. References + graders | Reference call lists, weighted checks, gates | Grader gauntlet (reference = 1, no-op = 0, mutants fail, determinism) |
| 6. End-to-end | Agent attempts per task | Solvability (pass@k > 0), difficulty band, failures routed to the earliest implicated stage with diff and trace |

### The repair loop and which feedback signals work

The "↓ world ↑ errors" loop works when errors are grounded, specific and local. AWM feeds back runtime exceptions "with problematic code snippets," capped at five iterations per component. It reached **86.8–88.3% first-attempt success and about 1.13 average iterations**, and allowed up to 10% failure per stage to control cost ([arXiv 2602.10090](https://arxiv.org/html/2602.10090v3)). AutoEnv needed up to 40 rounds for game worlds and finished at 65% end to end. Human review of the input theme raised success from 60% to 80% ([arXiv 2511.19304](https://arxiv.org/html/2511.19304)), which shows that vague specs are a major failure source. "Is Self-Repair a Silver Bullet?" adds a caution: gains are "often modest" once cost is counted. Models are "held back by their inability to reliably produce accurate and useful feedback," and repair depends on diversity among the initial candidates ([arXiv 2306.09896](https://arxiv.org/abs/2306.09896)).

From these sources, feedback signals rank as follows:

1. Validator errors with exact paths and codes. These are fixed nearly always within 1–3 rounds.
2. Constraint and referential-integrity violations.
3. Runtime exceptions with the offending snippet.
4. **Failing task oracles with an expected-versus-actual state diff.** This is the only signal that reliably catches semantic bugs.
5. Intermediate-value traces, which LDB reports improve on self-debugging by up to ~9.8% ([arXiv 2402.16906](https://arxiv.org/abs/2402.16906)).
6. LLM self-critique. It should only explain a grounded failure, never decide pass or fail.

The ranking is a synthesis of these sources. No study compares error formats head to head. Several practical controls follow from the same sources. Reject invalid writes at the interface, as SWE-agent's linter-gated edit does ([arXiv 2405.15793](https://arxiv.org/abs/2405.15793)). Keep previously passing checks as regression "anchors," as AlphaCodium does ([arXiv 2401.08500](https://arxiv.org/abs/2401.08500)). Cap retries at about 3–5 per stage. Revert patches that increase the error count. Escalate to a stronger model or an upstream stage when the same error fingerprint repeats. GIF-MCTS's Generate/Improve/Fix tree search is the principled version of that escalation ([arXiv 2405.15383](https://arxiv.org/abs/2405.15383)). Every engine error should carry a stable code, a path, expected and actual values, and the owning stage. The error message is the interface between the engine and the model, so it deserves snapshot tests like any other API.

### Budget and post-generation testing

Cost is not the constraint. AWM spent **$57.09 per 100 worlds with GPT-5**, EnvScaler about **$1.02 per world** (mostly its 100-round behavioral test), and AutoEnv **$4.12** ([arXiv 2602.10090](https://arxiv.org/html/2602.10090); [arXiv 2601.05808](https://arxiv.org/html/2601.05808); [arXiv 2511.19304](https://arxiv.org/html/2511.19304)). With model credits, the builder can spend on more candidates per stage and more verification rollouts, which is where the evidence says money buys quality. After generation, behavioral fuzzing adds a further gate:

- EnvScaler-style random positive and negative tool calls;
- Schemathesis, which "chains operations with real response data" across create → get → update → delete ([Schemathesis](https://schemathesis.readthedocs.io/en/stable/explanations/stateful/));
- Hypothesis `RuleBasedStateMachine` with domain invariants that "run after every step" and shrink failures to minimal reproductions ([Hypothesis](https://hypothesis.readthedocs.io/en/latest/stateful.html)).

Formal specs are not ready as generation targets. LLMs reached **only 8.6% semantic correctness** writing TLA+ ([AI4FM](https://ai4fm.cs.luc.edu/papers/gsirs-2026-tla-llm/)).

### Simulated users belong in the world

For conversational worlds such as a helpdesk with a customer on the line, a single-control LLM user is noisy: **40–47% of simulated retail and airline conversations contained a user-simulator error**. Telecom's dual-control setup, where the user has its own tools and state, brought this down to **16%** ([arXiv 2506.07982](https://arxiv.org/html/2506.07982)). The same move from no-user to dual-control mode cost gpt-4.1 18 points, so the user design itself changes the benchmark ([arXiv 2506.07982](https://arxiv.org/html/2506.07982)). WorldGen should give any simulated user a scripted goal plus state-grounded tools, grade on world state rather than user satisfaction, and sample transcripts to report the simulator's own error rate.

## browser-use is an agent harness for a UI layer, not part of the engine

browser-use is an MIT-licensed Python framework with **about 117k GitHub stars**. It lets any LLM drive Chromium over the Chrome DevTools Protocol by serializing the DOM into an indexed element list plus screenshots, with **31 browser actions** ([browser-use](https://github.com/browser-use/browser-use)). It has no reset, no state probes and no programmatic reward. Its own benchmark grades **200 live-web tasks with an LLM "findings judge"** using a weighted rubric ([browser-use/benchmark](https://github.com/browser-use/benchmark)). That is precisely the noisy grading regime that a state-owning engine avoids: LLM judges on live sites ran at about 82.6% agreement with humans in InSTA ([arXiv 2502.06776](https://arxiv.org/abs/2502.06776)).

The right fit is downstream. If a world also exposes a web UI over the same engine state (a later stage, since the spec centers on APIs), browser-use can drive it unchanged as one agent harness: point it at a localhost URL, run its `Agent` as one episode, then call the engine's admin `grade` endpoint. REAL's `/finish` endpoint on its clones is the precedent ([arXiv 2504.11543](https://arxiv.org/pdf/2504.11543v1)). This gives browser-use something its live-web benchmark lacks: deterministic tasks graded on state. browser-use also has two secondary uses: a strong baseline agent for difficulty calibration, and a smoke tester that checks generated UIs are actually operable, similar to FullStack-Agent's GUI-agent-based testing ([arXiv 2602.03798](https://arxiv.org/html/2602.03798)). For RL rather than evaluation, BrowserGym's gym-style step/reset/reward API is a closer structural match ([arXiv 2412.05467](https://arxiv.org/abs/2412.05467)). The notes did not confirm whether browser-use exposes a step-level API, so plan around episode-level integration.

### What the evidence does not yet settle

Several open questions remain. Most 2026 synthesis papers (ClawEnvKit, CompoWorld, VERA, WorkForge) were read at abstract level only, so their repair-loop statistics are unknown. No published study compares staged against one-shot world generation, DSL against Python targets, or SQLite against container reset latency. No public source shows how vendors such as Fleet or Turing build replicas internally.

## Conclusion

The research changes where the difficulty lies. Generating runnable world code is largely solved: about 87% first-pass success and roughly one repair round per stage, for under a dollar per world. What remains open is whether a generated world tells the truth about the agent. Bugs in generated worlds are the norm, evaluators disagree with humans on roughly one task in five, and models game graders they can see. A WorldGen that wins on spec-to-app fidelity alone would join the market's "vibe-coded buggy websites." One that emits worlds whose graders have been mutation-tested, whose tasks have been oracle-solved and no-op-failed, and whose state is hash-deterministic would offer something neither papers nor vendors currently package. That makes the engine's validation gauntlet and its error messages the real product surface. The generator is a client of the engine.

The less obvious implication is that the engine's strictness is what lets the generator succeed. Semantic bugs survive LLM self-repair but not oracle-backed state diffs. So every invariant the engine checks statically or enforces at runtime is one the generator no longer needs to get right. That argues for investing first in a narrow, declarative, heavily checked world format and its error catalog, then scaling generation, and widening the format only when measured failures show the DSL cannot express what users ask for. The same structure also produces training data: verified reference solutions, mutants and pass^k runs make every passing world an RL environment as well as an eval.
